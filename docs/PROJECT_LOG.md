# Codex-X 项目维护日志

本文件记录面向维护者的根因、设计决策、验证依据和遗留风险。它与
`CHANGELOG.md` 分工如下：

- `CHANGELOG.md` 面向用户，记录每个发布版本可感知的新增、调整和修复。
- 本文件面向开发维护，解释为什么修改、哪些约束不能破坏，以及如何验证。

日志不得包含 Token、认证文件内容、用户数据或仅适用于某台电脑的隐私路径。

## 2026-09-12：会话导出、Skills/MCP 归档与大日志统计

- 会话列表新增单条 Markdown 导出和多选 ZIP 导出，只包含明确选择的会话。复用活动 SQLite 与权威
  rollout 路径，验证存储根、普通文件和 session_meta.id，支持非标准文件名；正文按角色与事件类型筛选，
  过滤系统/工具/推理记录，以计数方式消除 event_msg 与 response_item 镜像，同时保留重复对话轮次。
  图片/音频使用占位，记录按行选择解析。单条记录仍有 64 MiB 保护上限，损坏或过大记录会报告部分导出。
- Skills/MCP 使用带版本 manifest 的 ZIP，保留配置、文件权限、空目录、启用状态和备注；当前标签页可导出
  全部内容，同一 ZIP 入口识别普通 Skill 包与 Codex-X 归档。本地 ZIP 取消压缩与展开后的 20 MiB 大小上限，
  使用 rfd 原生文件窗口和 Rust 文件流，避免大文件在前端 ArrayBuffer/整数数组及 IPC 中多次复制。
  本地归档可能包含 MCP 连接凭据，导出入口有保管提示；不上传归档或会话。
- ZIP 路径、重复路径、链接与特殊文件校验保留；导入预先检查所有同名冲突，不覆盖不同内容。
  MCP 配置与数据库变更共同回滚，失败移除本次创建的 Skill；导出临时文件使用受限权限、目标快照校验
  和原子替换，禁止写回应用数据目录。用户取消文件选择时不执行读写。
- 导入已有的假 stdio 项来自无效/空 MCP 配置的默认展示；候选现在必须具备有效 command 或 URL，
  预览与导入复用同一验证与去重路径，已存在的实时配置不再计入新增。兼容包装 JSON，正确处理
  config.toml 中 enabled=false 的条目。暗色弹窗补齐统计格子、列表文字、边框及警告区域的颜色。
- 用量扫描将 2 MiB 整行跳过改为 64 KiB 缓冲快路径与超长行流式反序列化，跳过大正文/图片字段，
  仍读取 token_count、模型与父子会话信息；保留增量偏移、扫描预算、坏行恢复和尾行补写规则。
- 验证：479 项 Rust 测试、45 项前端测试、类型检查和 macOS 构建通过，包含 >20 MiB ZIP、归档往返、
  冲突与错误回滚、导出正文去重、非常规会话路径，以及 >2 MiB 图片/工具/计费事件等回归。
  浏览器确认暗色导入弹窗、无新增提示、分标签导出、单/多会话导出与取消操作；本机确认原生打开/保存
  窗口可正常取消，原先的四个已有 MCP 不再被提示重新导入。本地 App 已替换，旧 App 和构建副本均经
  ZIP/二进制校验后归档，仅保留一份应用注册。尚未推送 GitHub。

## 2026-09-10：后台配置检查与可选修复

- 后续界面调整：将设置中的首次向导入口与配置检查卡片合并为同高的一行「环境与配置检查」。
  行内仅保留配置状态和检查按钮；环境详情、配置问题和修复方案统一放进原检查窗口。
  首次安装自动打开，普通手动检查不删除或重置首次使用标记；后台静默检查保持独立。
  环境检测加载或失败时窗口仍可打开，配置检查/修复继续可用；修改目录后需重新检查再提供修复，
  避免把旧目录结果误用于新目录。查看过的问题不再紧接着重复弹出后台提醒。
- 新增独立的只读检查 IPC；窗口可见且未编辑/写入配置时后台检查，回到窗口时唤醒。
  不依赖 get_codex_state 成功，也不占用供应商操作的 loading 状态。稳定错误需间隔至少 1 秒确认两次。
  同一目录的同一问题保存提醒记录；30 秒提醒支持直接修复和进入通用设置，忽略后提示设置入口。
  弹窗、隐藏窗口和其他通知期间暂停提醒计时；无关配置编辑更新修复指纹但不缩短剩余时间。
  临时缺失/空文件不会直接清除提醒记录，正常配置也经稳定确认后才允许以后再次提醒。
- 检查 TOML 语法和供应商表、名称、选择标识、认证开关及协议字段，保留 Codex 的合法默认值。
  依据 [Codex 配置说明](https://learn.chatgpt.com/docs/config-file/config-reference) 和
  [rust-v0.153.4 配置校验](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/config/src/config_toml.rs)：
  name 对普通自定义供应商必需，省略 base_url、wire_api、认证/WebSocket 开关本身不是错误。
  不把 Chat Completions 协议盲改为 Responses；无法确认的问题提供查看配置入口。
- 旧会话恢复可以使用数据库中的 model_provider，所以根配置正确时也要检查历史引用。
  只查询活动 SQLite 中最近 10,000 条记录的不同标识，不读取会话正文；有效的顶层 profile 配置可解释
  相应引用，避免误报。仅当缺失一个引用且有唯一完整来源时提供补齐方案，提示明确说明沿用哪个供应商。
  多个来源或无法确定时不猜测，不改数据库、auth、模型或其他配置文件。
- 修复只在用户点击后执行：备份、文件锁、配置/认证判断/会话引用/profile 指纹复核及原子写入。
  外部修改使旧方案失效；符号链接配置不覆盖。错误提示不包含源文件行或凭据。
  这是供应商相关的有限检查，不宣称完整验证 Codex 所有扩展设置。
- 验证：445 项 Rust 测试、45 项前端测试、类型检查及构建通过。浏览器验证首页读取失败仍可进入设置修复，
  提醒到期后供应商可操作，额度弹窗期间提醒隐藏，关闭提醒后的设置提示可见，手动问题无自动修复按钮。
  本地 macOS App 已构建、签名校验、替换并启动；旧安装与构建副本均经完整 ZIP/二进制校验后归档，
  Launch Services 只注册 Applications 内的一份安装。此次尚未发布到 GitHub。

## 2026-09-09：重置次数查询与套餐徽标

- 额度弹窗新增独立只读重置卡请求，读取 rate-limit-reset-credits 的 available_count，仅展示可用次数。
  与 usage 请求同时发起，各自返回即更新，独立处理加载与错误；空字段和失败不当作零，刷新失败可保留
  对应上次结果并明示。关闭、重开、切换账号或目录后丢弃旧返回，不提供兑换操作。
- 原生请求共用敏感请求头、固定 HTTPS 地址、超时、响应大小限制和凭据复核。文件锁采用非阻塞方式，
  因此仅在读取/复核凭据时用短互斥协调两请求，网络阶段不持锁，后端并发回归验证两路可重叠执行。
- 官方摘要从自己拥有的认证解析套餐，与邮箱共用有界 JWT 读取，刷新及注销遵循同一归属规则。
  数据字段对照 [Codex token_data.rs](https://raw.githubusercontent.com/openai/codex/main/codex-rs/login/src/token_data.rs)，
  展示映射按用户要求区分 Pro 20x / Pro 5x；未知套餐中性显示，套餐徽标不作权限或认证依据。
- 邮箱改为外层对齐容器、内层随文字收缩的边框，字号由 10px 增至 12px，后接套餐徽标。
  Pro 20x 使用金色，Pro 5x 使用紫色，Plus/Team 等使用各自配色；列表邮箱列不受“当前使用”挤动。
- 验证：415 项后端测试、30 项前端测试及类型检查通过。浏览器确认两接口同时待返回，重置次数先
  显示时额度仍可独立加载；在 App 最小窗口下，邮箱边框贴合内容、字号为 12px，套餐并列且操作按钮不换行。
- 本地 App 已构建、签名校验、替换并启动；旧版本和构建副本均已校验压缩归档，只保留一份安装。

  同接口不同密钥保持隔离，多个候选且无已选 ID 时不猜测，不覆盖或新增重复项。
- 新增模型映射编辑，支持当前模型、已获取模型批量导入，以及自定义菜单名称、实际模型 ID 和上下文大小。

  启用时通过 Codex 的 model_catalog_json 加载实际模型目录，不改 models_cache.json。
  显示名称不影响发给供应商的模型 ID；模型能力采用保守默认值，未承诺图片、托管工具或推理参数支持。
- 目录生成放在旧版简略模板与当前配置合并之后，避免丢失公共设置或重新带入旧菜单。

  来源标记与内容摘要支持识别其他 CODEX_HOME 中生成的目录，避免跨目录切换残留菜单。

  清理冲突认证字段及 Authorization 头，其他请求头保留；供应商保存模板不包含明文 Bearer。

## 2026-09-08：模板同步与页面操作隔离、保留首次检测的供应商

### 根因与修复

- 后台模板同步本身仅设置 `promptSyncing`，但远程下载与模板内容读取共用长时间持有的互斥锁。
  同步期间查看/编辑或启用模板会等待该锁，前端共享的 `loading` 又会使供应商页面的按钮禁用。
  查看与启用现在依次使用本地修改、已提交的 SQLite 缓存和打包模板；联网更新统一由同步命令处理。
- 模板详情请求使用页面独立的加载状态。离开提示词页、切换配置目录、打开另一编辑对象时使旧请求
  失效，迟到的成功、失败及清理回调不能覆盖新的编辑草稿或其他页面的状态。
- 本地编辑允许与同步并行。同步清理在数据库事务中保留已有本地修改的模板，返回目录前再次读取
  最新修改记录，避免下载开始时的旧快照误删刚编辑过的下架模板。
- 首次显示的 CC Switch 供应商可能只是当前 Codex live 配置的检测结果，并未执行数据库导入。
  旧逻辑在切换前只更新已有的唯一匹配记录，因此未保存的检测项会在 live 配置被替换后消失。
  现在明确启用/切换时保存未匹配的当前第三方配置：在同一 SQLite 事务内完成匹配、分配不冲突的
  记录 ID 和保存，保留完整 TOML 与独立 API Key，切换失败时沿用条件回滚。多个匹配项不擅自覆盖。
- 当前供应商标记只接受与实际 live 配置匹配的已保存 ID；临时或冲突 ID 不覆盖后端识别结果。
  普通状态读取继续保持无配置写入，不触发 CC Switch 全量导入。

## 2026-08-11：供应商认证往返、模板完整性与启动读取

### 决策

- 新建和 CC Switch 导入的供应商保存完整、无密钥的 TOML 模板；API Key 单独保存在供应商
  数据库字段中。完整模板是该供应商的权威配置，切换时恢复项目、插件、MCP、桌面、功能和
  环境设置；旧版稀疏模板仍以当前 live 配置为底稿兼容合并。
- 官方 OAuth 只保存在 Codex-X 的独立可信快照和官方 live `auth.json` 中。切换第三方时，
  live `auth.json` 改写为只含 `OPENAI_API_KEY` 的第三方认证；第三方 TOML 不保留
  `auth_mode` 或 `experimental_bearer_token`，切回官方时再恢复完整官方认证。
- 官方配置独立保存完整 `config.toml`、模型和 OAuth/API Key `auth.json`。官方与第三方往返
  按目标方向写入：第三方凭据先于第三方路由，官方路由先于官方凭据；失败时只回滚已经写入
  的第一步。未登录的官方 Reset 快照也必须保留完整 TOML。自动捕获不得让第三方 API Key
  覆盖可信 OAuth 快照。
- 兼容无 `auth_mode` 但包含有效 token、且不含 API Key 的旧版官方 OAuth；损坏的 live

  认证快照。完整官方 TOML 是模型字段的权威源，独立模型输入只补齐缺失值。
- 启动状态读取不得迁移提示词、修改文件权限、捕获认证或扫描历史备份；概览在结果返回前显示

- Codex-X 内部数据库使用持久 `user_version`。已升级数据库的普通打开只读版本号；迁移、历史

- Codex 版本探测在 blocking worker 中执行，固定候选先探测，目录候选流式探测，所有阶段共享

  默认 `preserveCodexOfficialAuthOnSwitch = false` 路径：第三方认证直接写入 `auth.json`。

  兼容策略参考，不再作为 Codex-X 默认切换语义；

## 2026-07-30：live 配置并发与失败回滚

### 已确认根因

Codex-X 的供应商、提示词、备份恢复和状态刷新曾各自读写 `config.toml`。即使每次
写出的内容都是合法 TOML，只要 Codex、CC Switch 或另一条 Codex-X 操作在“读取旧值”和
“整文件替换”之间更新配置，后写入者就会覆盖前一个新值。多文件操作在中途失败时还可能
留下 config、auth、AGENTS 或应用数据库互不对应的混合状态。

### 约束

- 所有 Codex live 配置写入共用跨进程文件锁；已经持锁的内部函数使用 `_locked` 入口，
  禁止重复获取非重入锁。
- 写入前保存原始字节快照，原子替换前再次核对当前内容；快照已过期时拒绝写入并要求刷新。
- 回滚只能覆盖本次操作实际写出的期望值。多文件回滚先统一预检，再逆序恢复，不能覆盖
  Codex 或 CC Switch 在失败后写入的新内容。
- 活动供应商编辑从身份识别到数据库更新、live 热更新和最终状态构造都处在同一配置锁
  边界内。
- 备份恢复只接受备份根目录下的单个普通目录名和普通文件；元数据 ID、`CODEX_HOME` 与
  `had_config` / `had_auth` / `had_agents` 声明必须和实际载荷完全一致。损坏或缺失元数据、
  跨目录恢复、路径穿越、额外/缺失载荷和符号链接均在 live 写入前拒绝。旧提示词结构先在
  内存迁移，再作为一次可回滚写入落盘。
- 状态刷新在同一锁内完成旧配置迁移、官方认证捕获和状态构造；认证快照失败必须返回错误，
  不得吞掉后显示成功状态。

## 2026-07-30：关闭主窗口后驻留系统托盘

### 问题

Codex-X 原先没有系统托盘和窗口关闭事件处理。用户点击主窗口关闭按钮后，
Tauri 事件循环随最后一个窗口关闭而结束，后台管理能力也随之退出。

首版修复只调用了 `window.hide()`。这可以保留进程和窗口状态，但 macOS 应用仍是
`ActivationPolicy::Regular`，因此 Dock 图标不会消失，尚未真正进入仅菜单栏驻留状态。

### 决策

- 仅拦截标签为 `main` 的主窗口关闭请求，将窗口隐藏而不是销毁或结束进程。
- macOS 关闭时同时隐藏 Dock 并切换为 `ActivationPolicy::Accessory`；恢复窗口时切回
  `Regular`。这两项都执行，避免不同 macOS 版本残留 Dock 图标。
- Windows 关闭时显式启用 `skip_taskbar`，恢复时关闭，避免隐藏窗口仍占用任务栏。
- macOS 左键点击顶部栏图标打开菜单；Windows 左键点击托盘图标直接恢复窗口。
- 选择“显示 Codex-X”会恢复、取消最小化并聚焦原主窗口。
- 托盘菜单始终提供“退出 Codex-X”，用于明确结束后台进程。
- macOS 再次点击 Dock 图标时也恢复已经隐藏的主窗口。
- 不拦截应用级退出或更新器的显式重启，保证退出菜单、`Cmd+Q` 和安装更新仍可结束进程。

### 参考实现

对照 CC Switch `56fb46c09310ff52dabefd2b32f0e799e8357d9e` 的
`src-tauri/src/lib.rs` 和 `src-tauri/src/tray.rs`：其 Windows 路径使用
`set_skip_taskbar`，macOS 路径同时使用 `set_dock_visibility` 和
`set_activation_policy`。Codex-X 复用相同的平台生命周期规则，但保留自己的简化托盘菜单。

### 验证

- `cargo fmt --all -- --check`、`cargo check --locked --lib` 和 `git diff --check` 通过。
- `cargo test --locked --features windows-runtime-check` 全量通过。
- `pnpm --dir apps/desktop typecheck` 和 `pnpm --dir apps/desktop build:renderer` 通过。
- macOS 本机包实测：窗口显示时 Launch Services 类型为 `Foreground`；点击关闭按钮后
  主窗口消失、PID 保持不变，类型切换为 `UIElement`。这证明应用已从 Dock 模式进入仅
  顶部栏驻留模式；再次激活后同一 PID 恢复为 `Foreground`，配置数据正常加载。
- `Cmd+H` 后可以恢复同一进程；`Cmd+Q` 和托盘“退出 Codex-X”仍用于真正结束进程。
- 本机 Windows 交叉编译在第三方依赖 `ring` 阶段因缺少 MSVC C 头文件停止，尚未进入
  项目代码；发布前仍须以 GitHub Windows Actions 的原生构建结果为准。

## 2026-07-29：供应商切换与配置完整性

### 已确认根因

旧实现会把检测到的整份历史 `config.toml` 保存到供应商记录，并在后续切换时覆盖
当前文件。该文件仍可能是合法 TOML，但新增加的项目、插件、MCP 和功能设置会丢失，
表现为 Codex 要求重新设置或配置被“破坏”。

### 约束

- 供应商记录可以保存完整 TOML，作为导入与编辑模板；其中的密钥必须剥离并由独立字段保存。
- 激活供应商必须基于最新 live 文档，仅合并目标 provider 与 model 字段，不回放模板中的
  项目、插件、MCP 或其他通用设置。
- 官方认证快照与中转认证严格隔离，供应商切换不能覆盖可信官方认证。
- 自动捕获官方认证只接受明确的 ChatGPT 登录模式及 access/refresh/id token；代理路由下的
  API key 属于不可信来源，不能晋升为官方快照。
- 用户明确从已确认的官方 live 路由切换到第三方时，允许保存非空的官方 API Key 快照，
  以保证“官方 API Key → 第三方 → 官方”往返不会丢失认证；只读状态刷新仍不自动采信 API Key。
- 第三方密钥只写入活动 provider 表的 `experimental_bearer_token`，不写入 `auth.json`。
- 官方与第三方路由都使用稳定的 `custom` 会话分桶；官方 provider 不设置 `base_url`，继续
  使用真实 OpenAI 后端和独立保存的官方 `auth.json`。
- 编辑活动供应商必须原子更新原记录，不能通过“保存后再切换”制造副本。
- 切换只影响后续新建会话，不强制重启 Codex 客户端。

## 2026-07-29：会话供应商同步

### 决策

- 统一使用 Codex 可识别的 `custom` 共享分桶。
- 活动会话的唯一权威来源是当前存储根目录中最高版本的可读 `state_N.sqlite`；旧 SQLite、
  单独存在的 JSONL 和 JSONL 行数都不能当作会话数量。
- 扫描 JSONL 前先按活动 thread ID 和 SQLite 的 `rollout_path` 建立候选集。标准命名孤立
  文件和未被引用的非常规文件不读取、不计入活动 rollout，也不会因损坏而阻断同步。
- SQLite 一旦为线程提供 `rollout_path`，该路径就是唯一权威文件；不得再按 UUID 文件名
  回退并修改同 ID 的旧副本。权威路径缺失、不可读或越界时必须标记扫描失败并阻止同步。
- `rollout_path` 指向的文件必须包含与该 SQLite 记录相同的 `session_meta.id`；缺少元数据、
  ID 串线或多个线程引用同一个文件时必须阻止同步，不能只更新 SQLite 后报告成功。
- SQLite 明确引用的非常规 rollout 仅在 `sessions` / `archived_sessions` 内、且为非符号链接
  普通 JSONL 时处理；活动候选无法读取或解析时保持失败关闭，不能显示“已同步”。
- 只修改 rollout 元数据和活动 SQLite 线程索引中的 provider 字段。
- 不修改会话正文、工作目录、用户事件标记或全局界面状态。
- 备份和回滚只覆盖本次实际修改的会话存储。

### 来源说明

当前 `b-nnett/codex-plusplus` 源码没有 rollout JSONL/SQLite 分桶同步实现，不能把这部分
描述为对其逐行复刻；`custom` 共享分桶语义来自对 CC Switch 可验证实现和本地 Codex
存储行为的交叉检查。
